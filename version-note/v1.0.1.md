# retrykafka v1.0.1 — Kafka Transactions

Usando el contexto global del proyecto `retrykafka` y asumiendo que `v1.0.0` ya está estable, implementar soporte opcional para **Kafka Transactions**.

## Objetivo

Agregar un modo transaccional que permita coordinar atómicamente operaciones Kafka-to-Kafka.

El caso principal es:

```text
Consumer receives message
        │
        ▼
Handler fails
        │
        ▼
BEGIN TRANSACTION
        │
        ├── Publish Retry Message
        │
        └── Commit Original Offset
        │
        ▼
COMMIT TRANSACTION
```

La librería debe garantizar que, dentro de las garantías ofrecidas por Kafka Transactions:

```text
Retry Publish
+
Consumed Offset Commit
```

formen parte de la misma transacción.

---

# Problema que resuelve

Sin transacciones:

```text
Handler fails
      │
      ▼
Publish retry
      │
      ▼
SUCCESS
      │
      ▼
💥 Process crashes
      │
      ▼
Offset was not committed
```

Al reiniciar:

```text
Original message is delivered again
      │
      ▼
Retry message is published again
```

Resultado:

```text
Duplicate retry messages
```

Con transacciones:

```text
BEGIN TRANSACTION
      │
      ├── Publish retry
      │
      └── Commit original offset
      │
      ▼
COMMIT TRANSACTION
```

Si ocurre un fallo antes del commit:

```text
Transaction aborts
```

La publicación del retry no debe ser considerada visible para consumers configurados con el aislamiento transaccional correspondiente.

---

# API

El soporte transaccional debe ser opcional.

Default:

```go
retrykafka.New(
    retrykafka.WithBrokers("localhost:9092"),
)
```

Semántica:

```text
At-least-once
```

Modo transaccional:

```go
retrykafka.New(
    retrykafka.WithBrokers("localhost:9092"),
    retrykafka.WithTransactions(),
)
```

O evaluar una API más explícita:

```go
retrykafka.New(
    retrykafka.WithBrokers("localhost:9092"),
    retrykafka.WithProcessingGuarantee(
        retrykafka.Transactional,
    ),
)
```

Preferir la API que mejor permita agregar futuras garantías sin romper compatibilidad.

---

# Processing Guarantees

Definir explícitamente los modos disponibles.

```go
type ProcessingGuarantee int

const (
    AtLeastOnce ProcessingGuarantee = iota
    Transactional
)
```

El comportamiento debe ser explícito y documentado.

```text
AtLeastOnce
```

Significa:

```text
Retry publish
+
Offset commit
```

son operaciones independientes.

Pueden existir duplicados.

---

```text
Transactional
```

Significa que las operaciones Kafka-to-Kafka correspondientes deben ejecutarse dentro de una transacción cuando el driver Kafka utilizado soporte esa capacidad.

No afirmar:

```text
Exactly-once business processing
```

porque Kafka Transactions no hacen idempotentes side effects externos.

---

# Alcance transaccional

El modo transaccional debe aplicarse especialmente a:

```text
Main Topic
      │
      ▼
Retry Topic

Retry Topic
      │
      ▼
Next Retry Topic

Retry Topic
      │
      ▼
DLQ
```

La operación conceptual debe ser:

```text
Consume
   │
   ▼
Handler fails
   │
   ▼
BEGIN TRANSACTION
   │
   ├── Produce destination message
   │
   └── Send consumed offset to transaction
   │
   ▼
COMMIT TRANSACTION
```

---

# Success Flow

Evaluar cómo manejar el caso:

```text
Consume
   │
   ▼
Handler succeeds
   │
   ▼
Commit Offset
```

Determinar si debe:

1. permanecer como commit normal, o
2. utilizar una transacción también.

Documentar claramente el trade-off.

No agregar una transacción innecesaria si no existe producción Kafka asociada.

---

# Consumer Isolation

Documentar claramente que los consumers que participan en un flujo transaccional deben considerar el aislamiento apropiado para evitar consumir mensajes de transacciones abortadas.

La librería debe:

* configurar esto automáticamente cuando sea posible;
* validar configuraciones incompatibles;
* documentar las configuraciones que deben ser responsabilidad del usuario según el driver utilizado.

---

# Driver Capabilities

No acoplar el core directamente a una implementación concreta.

Definir capacidades explícitas.

Ejemplo conceptual:

```go
type Capabilities struct {
    Transactions bool
}
```

El driver debe poder declarar:

```text
Transactions supported
```

o:

```text
Transactions unsupported
```

Si el usuario configura:

```go
retrykafka.WithTransactions()
```

pero el driver no soporta transacciones:

```text
Return explicit configuration error.
```

Nunca hacer fallback silencioso a at-least-once.

---

# Transaction Interface

Diseñar una abstracción mínima.

No abstraer Kafka completo.

La interfaz debe existir únicamente para soportar:

```text
Begin transaction
Produce message
Send offsets to transaction
Commit transaction
Abort transaction
```

Evaluar una interfaz conceptual similar a:

```go
type TransactionalProducer interface {
    Begin(ctx context.Context) error

    Publish(
        ctx context.Context,
        message Message,
    ) error

    SendOffsets(
        ctx context.Context,
        offsets []Offset,
        groupID string,
    ) error

    Commit(ctx context.Context) error

    Abort(ctx context.Context) error
}
```

La implementación final puede diferir.

Priorizar:

```text
Minimal API
Clear ownership
No leaky abstraction
```

```text
   │
   ▼
COMMIT
```

```text
BEGIN
   │
   ├── Error
   │
   ▼
ABORT
```

```text

```

# Concurrencia

Kafka Transactions no eliminan automáticamente todos los problemas de concurrencia.

Analizar:

```text
Concurrent transaction usage
Producer ownership
Partition processing
Consumer rebalances
Shutdown during transaction
Transaction timeout
Offset races
Producer fencing
```

La implementación debe definir claramente si:

```text
One transactional producer
```

puede ser utilizado concurrentemente o si:

```text
Transaction ownership
```

pertenece a un único flujo de procesamiento.

Evitar múltiples goroutines manipulando la misma transacción sin coordinación.

---

# Rebalances

Analizar explícitamente:

```text
Consumer processing message
        │
        ▼
Transaction active
        │
        ▼
Consumer rebalance
```

La librería debe:

1. detectar la pérdida de ownership de la partición;
2. evitar commits inválidos;
3. abortar la transacción cuando corresponda;
4. permitir que Kafka reprocesse correctamente el mensaje.

No intentar confirmar offsets de particiones que ya no pertenecen al consumer.

---

# Shutdown

Durante shutdown:

```text
Shutdown requested
      │
      ▼
Stop accepting new messages
      │
      ▼
Finish or abort active transaction
      │
      ▼
Release consumer
      │
      ▼
Close producer
```

Definir timeout configurable.

Ejemplo conceptual:

```go
retrykafka.WithTransactionShutdownTimeout(
    30 * time.Second,
)
```

# Retry + Transaction Flow

Implementar y testear:

```text
Message
   │
Handler Error
   │
BEGIN TRANSACTION
   │
├── Publish retry.1
│
├── Send original offset
│
COMMIT
```

Si:

```text
Commit succeeds
```

el mensaje original no debe ser reprocesado por el mismo motivo.

Si:

```text
Commit fails
```

la transacción debe ser manejada correctamente y el mensaje original debe permanecer disponible para redelivery.

---

# DLQ + Transaction Flow

Implementar:

```text
Final retry fails
      │
      ▼
BEGIN TRANSACTION
      │
      ├── Publish DLQ message
      │
      └── Send consumed offset
      │
      ▼
COMMIT
```

Así se evita el caso:

```text
DLQ published
      │
      ▼
💥 Crash
      │
      ▼
Original retry delivered again
      │
      ▼
DLQ published again
```

Dentro de las garantías del pipeline Kafka transaccional.

# Documentación

Crear:

```text
docs/transactions.md
```

Explicar claramente:

## Qué garantiza

```text
Atomic coordination between Kafka produced messages
and consumed offsets.
```

## Qué no garantiza

```text
Exactly-once execution of external side effects.
```

Ejemplo:

```text
Kafka Transaction
        │
        ├── Retry Topic publish
        └── Offset commit

External DB update
HTTP call
Payment
Email

NOT automatically atomic.
```

Recomendar IdempotencyStore para side effects externos.

# Trade-offs

Documentar:

## Ventajas

```text
Atomic Kafka-to-Kafka processing
Fewer retry/DLQ duplicates

Stronger guarantees
```

## Costos

```text
Higher latency
Potential throughput reduction
Driver requirements
Operational complexity
Transaction configuration

```

# Acceptance Criteria

La feature está terminada cuando:

```text
✓ Standard mode remains unchanged
✓ Transactions are optional
✓ Unsupported drivers fail explicitly
✓ Retry + offset can be committed atomically
✓ DLQ + offset can be committed atomically
✓ Aborted records are not processed by transactional-aware consumers
✓ Rebalances are handled safely
✓ Shutdown is safe
✓ No data races
✓ All tests pass
✓ go test -race ./... passes
✓ Documentation clearly distinguishes Kafka guarantees from external side effects
```

# Principio principal

La feature debe mejorar las garantías del pipeline Kafka sin convertir `retrykafka` en un framework pesado.

El usuario debe poder elegir:

```text
Simple by default:

At-least-once

Stronger guarantees when needed:

Transactional Kafka processing
```
